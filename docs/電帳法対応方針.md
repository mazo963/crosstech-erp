# 電子帳簿保存法への対応方針（帳票の発行・保存）

作成: 2026-10-31　対象: 見積書・納品書・請求書の発行と保存

> **この文書の位置づけ**
> 作成時点で国税庁の一次資料（一問一答・条文）を直接確認できていません（環境のネットワーク制限）。
> 法令の記述は、確認できた公開情報と作成者の理解に基づきます。**「要確認」と書いた項目は、税理士または国税庁の最新資料で確認するまで断定しないでください。**
> 実装は、解釈が分かれても成り立つ「発行時に内容を固定し、改ざん・削除を防ぎ、検索できる」方式にしています。

## 1. 前提（2026-10-31 に決定）

| 項目 | 内容 |
|---|---|
| 渡し方 | 取引先により **紙** と **PDF（メール等）** の両方 |
| 請求書 | 当面は **マネーフォワード（MF）が正式、ERPは控え・社内用**。POC完了後にERPへ移行する可能性あり |
| 移行への備え | ERPの請求書にも適格請求書の記載事項を最初から載せ、「控え／正式」は設定（`company_settings.erp_invoice_official`）で切り替える |

## 2. 制度の整理

電子帳簿保存法の対象は3区分。本システムとの関係は次のとおり。

| 区分 | 内容 | 本システムでの該当 |
|---|---|---|
| ① 電子帳簿等保存 | 自分でパソコン等を使って作った帳簿・書類を、電子データのまま保存する | ERPで作る見積書・納品書・請求書の**控え**。紙に出力して保存しても、電子データで保存してもよい（要確認: 紙で保存する場合は電子保存の要件は不要、という整理） |
| ② スキャナ保存 | 紙で受け取った書類をスキャンして保存する | **対応**（§4-2）。読取条件・入力期限・相互関連性・検索・タイムスタンプ。条件の数値は保守的に設定し**要確認** |
| ③ 電子取引データ保存 | 電子的にやり取りした取引情報を電子データのまま保存する。**2024年1月1日から義務** | **送付したPDF**（§4）と、**受け取ったPDF等**（外注先の請求書・領収書など。§4-2）の両方に対応 |

### 保存要件と本システムの対応

| 要件 | 内容（要確認を含む） | 対応 |
|---|---|---|
| 真実性 | 訂正・削除の履歴が残る、または訂正・削除ができない仕組みであること。タイムスタンプ付与、または事務処理規程のいずれかでも可（要確認: どれを選ぶと足りるか） | 発行済みの帳票は**更新・削除をDBが拒否**（トリガー）。特権ロールでも内容の書換えは不可。訂正は「取消＋新しい版の発行」で、旧版は残る。取消も理由を必須で記録 |
| 見読可能性 | 整然・明瞭に画面・書面で出力できること | 画面表示とブラウザ印刷（A4）。固定内容から描画するので、再印刷しても同じ |
| 検索機能 | 取引年月日・取引金額・取引先で検索でき、日付・金額は範囲指定、2項目以上の組合せができること。小規模事業者は不要になる条件あり（§3） | 帳票タブで、種類・取引年月日（範囲）・取引金額（範囲）・取引先・帳票番号を組合せ検索 |
| 関係書類の備付け | システム概要書、操作説明書等 | 本書、`docs/仕様書_v2.md`、`supabase/migrations/`、`README.md`（§7） |
| 保存期間 | 法人税: 原則7年（要確認: 欠損金の繰越控除を受ける事業年度は10年となる書類の範囲）。消費税（インボイス）: 7年 | **帳票・納品・請求・入金は削除しない**運用（CLAUDE.md §3-3）。バックアップは§6 |

## 3. 検索要件が不要になる条件（要確認）

- 電子取引データ保存では、**基準期間の売上高が5,000万円以下**の事業者などは、検索機能の確保が不要（税務職員の求めに応じて**ダウンロードできる**ことが条件）、という整理を確認（2024年1月以後の取引）。
- **要確認**: 令和7年度・令和8年度の税制改正で、金額の基準などが変更されていないか。国税庁の最新の一問一答で確認すること。
- 本システムは、条件に当たるかどうかにかかわらず検索機能を備える方針。ダウンロードの求めに備えたCSV出力は**未実装**（§6）。

## 4. 実装の内容

### データ（`20261031000006_issued_documents.sql`）
| テーブル | 役割 |
|---|---|
| `issued_documents` | 発行した帳票の**固定内容**（JSON）、SHA-256、版、取引年月日・金額・取引先（検索項目）、取消の有無 |
| `document_deliveries` | 交付の記録（紙／PDF／その他、交付日、宛先）。**追記のみ** |
| `document_files` | **送付したPDFそのもの**。ハッシュ・サイズはDBが計算。PDF以外・5MB超は拒否。**追記のみ** |

### 動き
1. 画面で「発行・表示」を押すと、DBの `issue_document` が金額・消費税を計算し、記載内容を固定して保存する。同じ内容なら既存の版を開き、内容が変わっていれば新しい版（旧版は残る）。
2. 印刷・PDF保存は**固定内容**から行う（元データが後で変わっても、発行時の帳票が再現される）。自社情報（住所等）も発行時点のものを固定する。
3. 元の請求書・納品が取消されたら、固定済みの帳票も自動で「取消」になる（行は残る）。
4. 交付したら、帳票画面で交付を記録する。**PDFで送った場合は、送ったPDFファイルを選択して保存する**（DBがハッシュを記録し、後から差替え・削除はできない）。

### 請求書のレイアウト（適格請求書の記載事項への対応）
| 記載事項 | 対応 |
|---|---|
| 発行者の氏名・名称、登録番号 | 自社情報から固定（`company_settings`） |
| 取引年月日 | 請求日・対象期間 |
| 取引内容 | 明細（製番・品名・納品書番号・納品日） |
| 税率ごとに区分した対価の額、適用税率 | `tax_breakdown`（税率・対象額） |
| 税率ごとの消費税額 | 同上。**請求書1枚・税率ごとに1回**だけ端数処理（`create_invoice`） |
| 交付を受ける事業者の氏名・名称 | 得意先名 |

- 複数税率に対応（§4-3）。請求書・見積書は税率ごとの内訳を表示し、軽減税率の明細には※を付ける。
- MFが正式な間は、請求書に「【ERP控え・社内用】」「（控え）」と明記し、MFの請求書番号を併記する。

### 4-2. 受領書類（電子取引・スキャナ保存）とタイムスタンプ（`20261101000008_received_documents.sql`）

**受領書類**（`received_documents`、画面は「受領書類」タブ）
| 項目 | 内容 |
|---|---|
| 登録できるもの | 電子データで受け取った書類（メール・Web・EDI等）と、紙を読み取った書類 |
| 検索 | 取引年月日（範囲）・取引金額（範囲）・取引先・書類の種類・保存の種類の組合せ |
| 改ざん防止 | 登録後は更新・削除ができない（特権ロールでも本体の書換えは不可）。誤りは「取消（理由必須）＋登録し直し」。取消しても行は残る。同じファイルの二重登録は拒否 |
| ハッシュ | SHA-256 をDBが計算して控える |
| 重要書類／一般書類 | 見積書・注文書は一般書類、それ以外は重要書類（保守的な区分。**要確認**） |
| 入力期限 | 授受日から7営業日（早期入力）、授受日の2か月後から7営業日（業務処理サイクル）。営業日は**土日のみ除外**（祝日は考慮しない = 期限が早めに出る）。登録の時点で early / cycle / late を判定。超過していても登録は受け付け、「期限超過」と表示する |
| 相互関連性 | 取引先・関連する伝票番号（メモ）を記録。外注仕入（`purchases`）への紐づけ列あり（画面は未対応） |

**スキャナ保存の読取条件**（DBが登録時に確認。条件を満たさないものは登録できない。**数値・条件は保守的な設定で、一次資料で要確認**）
- 解像度 200dpi 以上、カラーまたはグレースケール（白黒2値は不可）、ページ数、PDF・PNG・JPEG・TIFF
- 読取日が授受日より前、または未来でないこと
- 入力者は、ログインしたユーザーを自動で記録
- 読取装置の設定値（解像度・色）は**入力した値を記録する**運用。ファイルの実際の解像度を自動測定はしていない
- 原本の廃棄日は記録していない（運用で、登録とタイムスタンプの付与を確認してから廃棄する）

**タイムスタンプ**（`document_timestamps`、Edge Function `timestamp`）
| 項目 | 内容 |
|---|---|
| 対象 | 受領書類、送付したPDF（`document_files`）。発行帳票の固定内容にも対応できる |
| 方式 | 対象のSHA-256を時刻認証局（TSA）へ送り、RFC 3161 のトークンを受け取って**そのまま保存**（追記のみ）。登録・PDF保存のたびに自動で依頼する |
| 確認 | 応答が「許可」で、ハッシュと nonce が要求と一致し、時刻がトークンの時刻であることを確認。DBは、対象のハッシュとの一致、時刻が未来でないこと・対象の登録より前でないことを確認 |
| 期限 | 付与時刻が、授受日（送付PDFは送付日）の2か月後から7営業日以内（日本時間の暦日）。範囲内=付与済み、超過=付与済み（期限後）、未付与で期限内=付与待ち、未付与で期限超過=期限超過。一覧に出し、期限超過の件数を強調 |
| 再検証 | `scripts/verify_timestamp.sh`（OpenSSL）でトークンの署名・証明書・ファイルのハッシュを検証できる。CA証明書は事業者から入手 |
| テスト | OpenSSL で作ったテスト用TSAの本物の RFC 3161 応答で、要求の作成・応答の解析・トークンの検証を確認済み |

**タイムスタンプの限界（重要）**
- **認定事業者との契約が必要**: 電帳法のタイムスタンプは、認定を受けた時刻認証事業者のものである必要がある（**要確認**: 認定の根拠と、対象となる事業者・サービス）。現状は事業者が未定のため、`TSA_URL` / `TSA_NAME` / `TSA_AUTH` の secret が未設定。**設定するまで付与は「保留」になり、一覧に期限つきで残る**。テスト用の局（OpenSSLやフリーの局）の付与は、法令上のタイムスタンプとして使わないこと。
- 事業者によって API が RFC 3161 互換でない場合は、`timestamp` 関数の通信部分を差し替える必要がある。
- 関数内では署名・証明書の検証は行わない（応答の整合性まで）。署名の検証は再検証スクリプトで行う。
- タイムスタンプを付与すれば、訂正削除の履歴を残す仕組みは必須でなくなる、という整理がある（**要確認**）。本システムは両方を備える。

### 4-3. 税率（`20261101000007_tax_rates.sql`）
- **税区分**（標準・軽減・追加可）と、区分ごとの**期間つき税率**をデータで持つ。税率の追加・変更にコードの変更は不要（画面「税率」タブ、管理者のみ）。
- 品目が税区分を持ち、**納品の記録時に「納品日時点の税率」を納品行に固定**する（資産の譲渡等の時の税率）。税率を後から変更しても、固定済みの納品・請求は変わらない。
- 請求書は税率ごとに集計し、消費税は**請求書1枚・税率ごとに1回**だけ端数処理。見積書は見積日時点の税率で計算。
- 守り: 管理者のみ変更可。その日以降の納品がすでにある税区分は、さかのぼって変更できない。適用期間の重複は不可。税率が登録されていない日付の納品は拒否（黙って別の税率を使わない）。
- **将来の税率（来年1月から予定されているとのご指摘の1%など）は登録していない**。公表・施行内容を一次資料で確認できていないため。確定したら、画面の「税率」から適用開始日つきで登録する（対象の品目の税区分の付け替えも必要になりうる）。

## 5. 運用ルール

1. 帳票は必ずERPの「発行・表示」から出す（ブラウザで画面を直接印刷しない）。
2. 取引先に渡したら、その日のうちに交付を記録する。PDFで送ったときは、**送ったファイルを必ず登録**する。
3. 訂正は、元の請求書／納品を取消して、新しく発行し直す（旧版は消えない）。
4. 帳票・入金・納品を、DBの管理画面から直接書き換えたり削除したりしない。
5. `service_role` キーと、DB管理者のパスワードは、必要な人だけが持つ（これらは固定内容の保護トリガーを無効にできるため）。

## 6. 未対応・リスク（優先順）

| # | 内容 | 影響 | 対応案 |
|---|---|---|---|
| 1 | **バックアップ**: Supabase無料プランの自動バックアップの有無・保持期間は**要確認**。7年保存の根拠となるデータが失われるリスク。受領書類のファイルもDBに入るため、容量（無料プランは500MB程度。**要確認**）にも注意 | 保存義務違反、復旧不能 | 有料プラン（日次バックアップ）、または GitHub Actions で毎日 `pg_dump` を暗号化して別の場所へ保存。**本番運用の前に必須** |
| 2 | **タイムスタンプの認定事業者が未契約**（§4-2）。契約・設定までは付与が保留になる | 付与期限を過ぎると、タイムスタンプ以外の要件（訂正削除の履歴）に頼ることになる | 事業者を選び、secret を設定。選定・契約は税理士にも相談 |
| 3 | **送付PDFの登録が手動**: 登録を忘れると、電子取引データの保存漏れになる | 保存義務違反 | PDFをサーバー側で生成して自動保存（Edge Function）。メール作成の前に「PDFを登録」を必須にする |
| 4 | **ダウンロードの求め**に応じるCSV出力が未実装 | 検索要件を免除される前提が崩れる | 帳票・受領書類の一覧をCSVで出力する機能を追加 |
| 5 | 受領書類の**自動取り込み**（メール添付の自動保存）は未対応。登録は手入力 | 登録漏れ | 受信専用アドレス＋取り込み機能 |
| 6 | スキャナ保存: 読取装置の設定値は**自己申告**。原本の廃棄日は未記録。外注仕入（`purchases`）への紐づけ画面が未対応 | 読取条件の証明が弱い | 画像の実解像度の自動測定、廃棄日の記録、紐づけ画面を追加 |
| 7 | **事務処理規程**（電子取引の訂正・削除の防止）の整備 | 仕組みで防止していれば不要となる可能性もある（要確認） | 税理士に確認し、必要ならひな形で作成 |
| 8 | **会計帳簿**（仕訳帳・総勘定元帳）は本システムの対象外 | 会計ソフト側の責任 | 会計ソフト側の電帳法対応を確認 |
| 9 | ブラウザ印刷はブラウザ・設定で見た目が変わる | 控えと実物の差 | 送付PDFを登録することで担保（#3で自動化） |
| 10 | 将来の税率（1%など）は未登録。法改正の内容は**一次資料で未確認** | 施行日に税率が合わない | 確定後に「税率」から登録。インボイスの記載事項の変更がないかも確認 |

## 8. 税理士に確認すること

1. ERPで作る見積書・納品書の控えを、紙で保存する／電子データで保存する、のどちらを正とするか。電子で保存する場合に満たすべき要件。
2. 請求書をMFで発行している間、ERPの請求書（控え）は国税関係書類に当たるか。当たる場合の保存方法。
3. PDFで送付した帳票の保存方法（本書の方式で足りるか）。検索要件の免除に当たるかの判定（基準期間の売上高）。
4. 保存期間（7年・10年の別）と、バックアップの方法。
5. 事務処理規程の要否。
6. 令和7年度・令和8年度の改正で、上記が変わっていないか。
7. ERPへ請求書を移行する時期の、適格請求書としての表示・運用の確認。
8. スキャナ保存の読取条件（解像度・色・入力期限・重要書類／一般書類の区分）と、タイムスタンプの要否・認定事業者の選定。
9. 来年1月からの税率変更の内容と、請求書・帳票の記載事項への影響。
