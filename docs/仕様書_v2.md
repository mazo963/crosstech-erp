## 1. 元仕様の問題点と、v2での対応

| # | 元仕様の問題 | 運用で起きること | v2での対応 |
|---|---|---|---|
| 1 | 締め日を設定するのに、請求書は案件ごとに1枚 | 月末締めで複数案件をまとめられない | **締め請求**：得意先×締め期間で1枚。未請求の納品行をまとめる（`create_invoice`） |
| 2 | 入金を記録する機能がない | 「未回収残高」が計算できない | **入金登録と自動消込**（古い請求から順に充当。振込手数料の差引にも対応） |
| 3 | 外注先に締め日はあるが、仕入・支払の記録がない | 外注費の実額と支払状況が分からない | **外注仕入テーブル**（品目に紐づけ、支払日を記録） |
| 4 | 初期パスワードがマニュアルに記載（admin / crosstech） | GitHubや資料から漏れる | **Supabase Auth**（メール＋パスワード）。初期管理者はSupabase管理画面で作成。固定パスワードは使わない |
| 5 | 消費税・インボイスの扱いが「10%を自動反映」のみ | 端数処理の誤り、登録番号や振込先の漏れ | 税は**請求書1枚・税率ごとに1回**の端数処理（切捨て/四捨五入/切上げを選択）。自社の登録番号・振込先を帳票に印字 |
| 6 | 受注・生産管理システムと、案件・製番を二重入力 | 入力の手間、製番の食い違い | **ERPが親**。製番はERPで1回だけ登録し、受注システムの進捗は製番で読み取り同期 |
| 7 | データの保存方式が未定義（受注システムは Drive に全件上書き） | 同時入力で後勝ち。金額データが消える | **PostgreSQL（Supabase）**。1件ずつ保存し、制約とトリガーで整合性を保証 |
| 8 | 「単一ファイルのコード全体を再適用」する運用 | 差分を追えない。AIでの改修も不正確になる | GitHubで管理。ファイルを分割し、DB変更はマイグレーションで追加 |
| 9 | 平均粗利率 = 全案件の利益率の平均 | 小口案件の率に引っ張られ、実態とずれる | **加重平均（総粗利 ÷ 総売上）**を主にし、単純平均は参考表示 |
| 10 | 納品記録の取消・訂正がない | 誤入力を直せない、または消して履歴が残らない | 納品は**取消（理由必須）**。請求済みの納品は、請求書の取消が先 |
| 11 | ステータスを手で切り替える前提が混在 | 進捗と表示が食い違う | 人が決めるのは「見積/受注/失注/完了」だけ。分納中・納品完了・請求済みは**データから自動算出** |
| 12 | メールのPDF添付ができない | 手でドラッグ＆ドロップ | v2初版は mailto で宛先・件名・本文を自動入力。次段階で、GAS（Gmail下書き）による**PDF添付済みの下書き作成**を検討 |

## 2. 業務フロー

```
見積（案件登録・品目入力 / AI取込で下書き）
  ↓  見積書を印刷・メール
受注（status=ordered、客先注文番号）
  ↓  製番ごとに受注・生産管理システムへ（加工現場）
加工 ── 受注システムの「加工完了」を、製番で読み取り同期
  ↓
分納（納品を記録 → 納品書。超過納品はDBが拒否）
  ↓
締め請求（得意先の締め日で、未請求の納品をまとめて請求書を作成 → 発行）
  ↓  MF併用中は、MFで正式発行し、番号を控える
入金（入金登録 → 自動消込 → 未回収残高・期日超過）
```

## 3. マスタ

### 3.1 スタッフ
- Supabase Auth のユーザーに紐づく（`staff.id = auth.users.id`）
- 権限：`admin`（すべて）/ `office`（業務データの登録・更新）/ `viewer`（閲覧のみ）
- 操作者コード `worker_code`：`home` / `matsuda` / `other`（受注システム・在宅ダッシュボードと共通）

### 3.2 得意先
- 基本情報、インボイス登録番号（`T`＋13桁）
- 締め日：都度 / 5 / 10 / 15 / 20 / 25 / 末日
- 支払条件：当月・翌月・翌々月 × 当日 / 5 / 10 / 15 / 20 / 25 / 末日
- 計上基準：
  - `都度納品`：分納のたびに請求対象
  - `全数完納`：案件の全品目が納品済みになってから請求対象
- メール宛先：請求書用 TO / CC、納品書用 TO / CC

### 3.3 外注先
- 名称、担当者、連絡先、締め日、対応工程（表面処理・熱処理・追加工など）

### 3.4 自社情報
- 会社名、登録番号、住所、TEL、メール、**振込先**、税率、**端数処理**

## 4. 案件と品目

- 案件番号：自動採番 `CRO` + 年月4桁 + 連番2桁（例: `CRO261001`）
- 品目の社内製番：未入力なら `案件番号-行番号`（例: `CRO261001-3`）。既存の製番を手入力することも可 ※要確認
- 品目：品名、仕様、客先品番、外注先（空欄 = 自社加工）、数量、単位、買単価（原価）、売単価、納期
- 備考（帳票に印字）と、社内メモ（帳票に出さない）を分ける
- 粗利 = 売上（数量×売単価）− 原価（数量×買単価）。外注仕入の実額は別途集計

---

## 5. 分納と納品書

- 品目ごとに「今回の数量」を入力して記録 → 納品番号 `DN2610-0001` を採番
- 単価は**納品時点で固定**（後で品目の単価を直しても、過去の納品・請求は変わらない）
- 受注数量を超える納品、受注数量を納品済み数量より減らす変更は、DBが拒否する
- 取消は理由必須。請求書に載っている納品は取消できない

---

## 6. 請求

- 請求番号 `INV2610-0001`
- 作成時に、締め日（期間末）までの未請求の納品行を集める。期間の開始は「前回の請求の締め日の翌日」
- 支払期日は、得意先の支払条件から自動計算
- 状態：下書き → 発行 → （取消）。入金消込済みの請求は取消できない
- MF併用中：MFで正式に発行し、`mf_invoice_no` に番号を控える

---

## 7. 入金

- 入金日、入金額、先方が差し引いた振込手数料、方法（振込・現金・相殺・その他）
- 消込額 = 入金額 + 手数料。期日の古い発行済み請求から順に充当
- 余りは「未消込の入金（過入金・前受）」として得意先残高に表示

---

## 8. ダッシュボード

| 指標 | 定義 |
|---|---|
| 総受注額 | 受注・完了の案件の売上合計 |
| 総粗利 | 同、粗利合計 |
| 粗利率 | 総粗利 ÷ 総売上（加重平均）。単純平均は参考 |
| 見積中の金額 | 見積状態の案件の売上合計 |
| 未請求額 | 納品済みで、まだ請求していない金額 |
| 未回収残高 | 発行済み請求の残高合計 |
| 期日超過額 | 支払期日を過ぎた残高 |

## 9. AI機能（Sonnet / Haiku）

| 機能 | 入力 | 出力 | 既定モデル |
|---|---|---|---|
| 見積依頼の取込 | メール本文の貼り付け | 得意先候補、品目（品名・数量・材質・板厚・納期）、備考 | Haiku |
| 注文書の取込 | 注文書PDF | 客先注文番号、品目、数量、単価、納期 | Sonnet（PDF・表の読み取り） |

運用ルール：
- AIの結果は**下書き**。人が画面で確認・修正してから保存する
- 得意先は、既存マスタとの照合候補を出すだけ（自動で新規作成しない）
- 1回ごとにモデル名・トークン数を `ai_extractions` に記録。月の上限（`AI_MONTHLY_TOKEN_LIMIT`）を超えたら停止
- APIキーは Supabase の secret に保存し、画面（ブラウザ）には渡さない
- モデルIDは環境変数で指定し、新モデルへの切替をコード変更なしで行う

## 10. 受注・生産管理システムとの連携

```
ERP（親）                         受注・生産管理システム（加工現場）
 案件・品目・製番 ─────────────→  ※当面は人が製番で登録（自動連携は次段階）
 project_items.juchu_* ←── 読取 ── doGet の受注JSON（items[].productNo で照合）
                                  isCompleted / completedAt / shippedDate
```

- ERPは受注システムへ**書き込まない**（Drive全件上書き方式のため、競合を起こさない）
- 同期は画面のボタン（＋必要なら定期実行）で、Edge Function `juchu-sync` が行う
- ハブのデータ契約に「ERPが読む項目」として `productNo`, `isCompleted`, `completedAt`, `shippedDate` を追記すること

## 11. セキュリティと運用

- 画面のURLを知っていても、ログインとスタッフ登録がなければデータは見えない（RLS）
- 認証なしで呼べるのは、休止防止用の `ping()` だけ
- 金額・状態の変更は `audit_log` に記録（閲覧は管理者のみ）
- **Supabase無料プランの注意**：利用が少ない状態が7日間続くと休止する。GitHub Actions で毎日 `ping` を呼んで防ぐ。無料プランは自動バックアップが弱いため、定期的にエクスポートするか、本番運用前に有料プランを検討する
- **リポジトリの公開範囲**：現在 public。秘密情報はコミットしないこと。private にする場合、GitHub Pages を使うには有料プランが必要
